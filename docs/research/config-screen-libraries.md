# Config screen libraries and config approach: Minecraft 1.21.1 through 26.2

Research for [issue #12](https://github.com/imyifeng/whos-after-me/issues/12), feeding the config-approach decision ticket (#13).
Date: 2026-09-08. Primary sources: [Modrinth API](https://api.modrinth.com/v2/) (`/project/<slug>/version` for `cloth-config`, `yacl`, `midnightlib`, `modmenu`, queried 2026-09-08), library source trees and branches inspected via the GitHub API (`shedaniel/ClothConfig`, `isXander/YetAnotherConfigLib`, `TeamMidnightDust/MidnightLib`, `TerraformersMC/ModMenu`), maintainers' mavens (`maven.shedaniel.me`, `maven.isxander.dev`, `maven.terraformersmc.com`, `maven.midnightdust.eu`), and the [MidnightLib wiki](https://www.midnightdust.eu/wiki/midnightlib/). Build anchors per the toolchain decision: 1.21.1, 1.21.4, 1.21.8, 1.21.11, 26.1.2, 26.2.

## TL;DR

1. **All three libraries plus Mod Menu are alive and cover all six anchors on Fabric** — every candidate has a published Fabric build for 1.21.1, 1.21.4, 1.21.8, 1.21.11, 26.1(.2) and 26.2 on Modrinth as of 2026-09-08. None is unmaintained; the real question is not availability but effort and API churn across the break.
2. **All four also crossed the 26.1 no-remap break properly.** Cloth Config's `v26.1`/`v26.2` branches build with `dev.architectury.loom-no-remap`; YACL split into a dedicated 3.9 line for 26.1+; MidnightLib literally ships two build scripts (`build-obfuscated` vs `build-unobfuscated-fabric.gradle.kts`); ModMenu's 26.x branches use the new `net.fabricmc.fabric-loom` plugin. Each publishes 26.1/26.2 artifacts against the unobfuscated Mojang-name game.
3. **There is at least one real 26.x-era API break in each library line:** Cloth Config removed the `AutoConfig.getConfigScreen(...)` convenience entry point in v26.1 (present through v21.11); YACL moved 26.1+ to a separate 3.9 release line (builder API shape unchanged); MidnightConfig's consumer API is unchanged; ModMenu's `ModMenuApi` shape is unchanged but its underlying types switched from Yarn (`Screen`/`Text`) to Mojang (`Screen`/`Component`) names.
4. **YACL and MidnightLib are themselves Stonecutter workspaces** (per-version `versions/` dirs; YACL ports 26.3 snapshots within days) — they consume exactly the toolchain this repo settled on, and both publish plain maven artifacts usable per Stonecutter subproject.
5. **Effort ranking for the mod's minimal v1 config (toggle, keybind, radius, indicator size/opacity):** MidnightConfig is the least code (annotated static fields, auto JSON persistence, auto screen, one-line ModMenu hook) but has **no keybind entry type**; Cloth Config and YACL give builder-API screens (Cloth additionally has a keybind entry; YACL does not) but persistence and screen wiring are manual; a hand-rolled GUI is feasible (Gson is bundled in the game) but costs an estimated 250–400 lines and absorbs all per-version GUI API churn on six anchors itself.
6. **ModMenu — the standard entry point to any config screen — is actively maintained and present on all six anchors** (stable releases from 11.0.4 on 1.21.1 to 20.0.1 on 26.2, 26.3 port merged 2026-07-23), and its `getModConfigScreenFactory()` hook is stable across the break. Whatever library is chosen, the ModMenu wiring is one small class either way.

## 3. The 26.1 no-remap break: what each actually ships

The break (per the settled toolchain decision and the multi-version tooling research): intermediary remapping ends at 1.21.11; from 26.1 the game is unobfuscated with Mojang names (JDK 25) and Loom splits into remap and no-remap plugin ids — "no mods from 1.21.11 or before will work without, at a minimum, recompilation". Verified state per library:

- **Cloth Config** — `v26.1`/`v26.2` branches declare `dev.architectury.loom-no-remap` version `1.17-SNAPSHOT` (its `build.gradle`), i.e. genuinely built against the unobfuscated game; `fabric_api_version=0.152.1+26.2`, loader 0.19.3 in `gradle.properties`. **Breaking change found:** `AutoConfig.getConfigScreen(Class, Screen)` and `AutoConfig.getGuiRegistry(Class)` exist on every branch through `v21.11` and are gone from `v26.1` onward — `AutoConfig` shrank to `register`/`getConfigHolder`; consumers wanting the auto-generated screen must now construct `ConfigScreenProvider(manager, registry, parent)` with `DefaultGuiRegistryAccess` themselves. Also note the release versioning changed with MC (15.x → 17.x → 19.x → 21.11.x → 26.1.x → 26.2.x), so one dependency line spans all anchors only by listing six versions.
- **YACL** — split 26.1+ into its own release line: 3.9.0's changelog says "Split into multiple branches / Update to 26.1-pre-1"; 3.8.x covers 1.21–1.21.11, 3.9.x covers 26.1/26.2/26.3-snapshots. The build is ModStitch (`dev.isxander.modstitch.base`) over Loom with per-version subprojects. The core API shape survived: `YetAnotherConfigLib.createBuilder()…build()` + `generateScreen(parent)` still exist on the 26.x line (checked `dev.isxander.yacl3.api.YetAnotherConfigLib` on `main`). Documented 26.1-era behavioral break: "ItemController can no longer render items before dynamic registries are loaded, due to a constraint of Minecraft's" (3.9.0 changelog). A new optional auto-serialization path (`config.v2.ConfigClassHandler` + Gson serializer) exists alongside the manual-binding builder.
- **MidnightLib** — the clearest mirror of this repo's own toolchain split: its Stonecutter workspace has separate `build-obfuscated.gradle.kts` and `build-unobfuscated-fabric.gradle.kts`, the latter applying `net.fabricmc.fabric-loom` 1.15-SNAPSHOT with the comment "For unobfuscated releases (>= 26.1)". The consumer API (`MidnightConfig.init(modid, class)`, `@Entry` fields, `MidnightConfig.getScreen(parent, modid)`) is identical on both sides of the break — a mod's per-version source needs no config-code fork.
- **Mod Menu** — 26.1/26.2/26.3 branches use `net.fabricmc.fabric-loom` (1.15/1.17-SNAPSHOT); ≤1.21.11 branches use the old remapping `fabric-loom`. The `ModMenuApi.getModConfigScreenFactory()` hook is textually stable across the break, but its types renamed: the 1.21.11 branch imports Yarn `net.minecraft.client.gui.screen.Screen`/`net.minecraft.text.Text`; the 26.3 branch imports Mojang `net.minecraft.client.gui.screens.Screen`/`net.minecraft.network.chat.Component`. A mod therefore writes its ModMenu hook twice under Stonecutter (or behind a preprocessor conditional) regardless of library choice.

Practical conclusion for the spec: no candidate is excluded by the break; the per-version cost is limited to (a) pinning two artifact lines for Cloth Config/YACL-era versioning and (b) the unavoidable Mojang-name rewrite of screen wiring code that even hand-rolled code pays.

## 4. Screen-building effort

What the mod needs for v1: master enable (boolean), toggle/keybind, detection radius (int slider), indicator size and opacity (float sliders) — i.e. one keybind plus four numeric/boolean entries.

- **Cloth Config** — two styles. (a) Manual: `ConfigBuilder`/`ConfigCategory`/`ConfigEntryBuilder` (v26.2 exposes 24 `start*` entry factories including `startIntSlider`, `startDoubleField` and `startModifierKeyCodeField` — the only candidate with a **built-in keybind entry**); the `save()` callback is yours. (b) `AutoConfig`: annotated config class (`@Config`, `@ConfigEntry`) auto-generates both GUI and persistence (Jankson/Gson serializers ship in the jar). Post-26.1, style (b) lost its one-line screen entry point (see §3), which pushes mods toward the manual builder or a hand-rolled `ConfigScreenProvider` call.
- **YACL** — pure builder API: `Option.createBuilder().binding(default, getter, setter).controller(...)` inside `ConfigCategory`/`OptionGroup`; controllers cover boolean, int/float/double field and slider, string, enum, dropdown, color, item, label, button, cycling lists — **no keybind controller** (no `KeyCode`/`KeyBind` type anywhere in the tree). Persistence is via the bindings (you write the save logic, typically a Gson file) or the v2 `ConfigClassHandler` + `GsonConfigSerializerBuilder`. Screen is one `generateScreen(parent)` call; ModMenu hook returns `lib::generateScreen`.
- **MidnightConfig** — annotation-driven: public static fields on a `MidnightConfig` subclass, `@Entry` for options (booleans, numbers, strings, enums, `Identifier`s, lists, colors, sliders via `isSlider`, file pickers) with `@Comment`/`@Condition` extras; `MidnightConfig.init("modid", Class.class)` in the main initializer persists to `config/<modid>.json` **via Gson** (`com.google.gson` — bundled with the game, MidnightLib imports it directly); the screen (`MidnightConfigScreen`, with categories/tab list, sliders, tooltips from `modid.midnightconfig.<field>` lang keys) is fully auto-generated; ModMenu wiring is literally `return parent -> MidnightConfig.getScreen(parent, "modid");`. It also ships a `MixinOptionsScreen` that adds a mod-options button to the vanilla Options screen. **No keybind entry type** — the toggle keybind would live in the vanilla Controls screen via `fabric-key-mappings-api-v1` (the usual mod pattern anyway) or a hand-built widget.
- **Hand-rolled** — extend the vanilla `Screen` (Yarn `net.minecraft.client.gui.screen.Screen` ≤ 1.21.11; Mojang `net.minecraft.client.gui.screens.Screen` on 26.1+), assemble `ButtonWidget`/`SliderWidget`/`TextFieldWidget`-type children in `init()`, handle parent return, resize, tooltips and save-on-close yourself. Persistence is a small Gson JSON file under `FabricLoader.getInstance().getConfigDir()` — Gson is bundled with the game (all three libraries above rely on it at runtime), so the serialization half is genuinely trivial; **vanilla `SimpleOption`/`GameOptions` is not a practical substitute** (it is hardwired to `options.txt` semantics and vanilla's own settings screen flow). Cost drivers: float sliders and a keybind widget are hand-written; every screen/widget class name follows the Yarn↔Mojang fork, so either two per-version source copies or a preprocessor conditional layer — exactly the churn a library otherwise absorbs for you. Realistic estimate for the v1 set: ~250–400 lines across the fork versus ~30–90 for the library options.

Rough code budget for the v1 config (screen + persistence + ModMenu hook, excluding lang files):

| Option | Config data | Screen | Persistence | ModMenu hook | Keybind entry |
|---|---|---|---|---|---|
| MidnightConfig | ~20-line annotated class | auto | auto (Gson JSON) | 1 line | **none** (use vanilla Controls) |
| Cloth Config (AutoConfig) | ~20-line annotated class | auto | auto (Jankson/Gson) | small (manual provider on 26.x) | yes (`startModifierKeyCodeField` for manual mode) |
| Cloth Config (manual builder) | POJO + ~90–130 lines | ~90–130 lines | yours (~30 lines Gson) | small | yes |
| YACL | POJO/builder ~90–130 lines (+ optional `ConfigClassHandler`) | builder | yours, or v2 Gson handler | 1 line (`lib::generateScreen`) | none (use vanilla Controls) |
| Hand-rolled | POJO | ~250–400 lines across Yarn/Mojang fork | ~30–50 lines Gson | 1 line (your own screen factory) | hand-built |

All three libraries are client-side UI concerns with harmless (or bundled) dependency graphs; the mod's config is client-only (HUD visuals), so none of them needs a server-side pairing. Whichever route is taken, ModMenu remains an optional dependency with a tiny entrypoint class — and per §2 it is safely available on all six anchors.

## 5. Options and trade-offs (input for ticket #13 — no decision here)

| Option | Strengths | Weaknesses / risks |
|---|---|---|
| **MidnightConfig (MidnightLib)** | Least code by far for the v1 scope; auto-screen + auto-Gson-persistence; stable API across the no-remap break; MIT license; designed to be JIJ-bundled (no user-side dependency install); itself a Stonecutter project; ModMenu hook is one line | No keybind entry (needs the vanilla-Controls pattern for the toggle key); single maintainer; smallest community of the three; screen look/UX is fixed by the library |
| **Cloth Config** | Richest entry catalogue incl. built-in keybind entry; optional `AutoConfig` annotation path; de-facto standard (huge install base, 165M Modrinth downloads); active multi-person bench porting each MC version | Two artifact lines to pin across the span (15.x…26.2.x); 26.1 removed `AutoConfig.getConfigScreen`, breaking the canonical ModMenu snippet; manual builder style still means hand-written persistence; LGPL-3 |
| **YACL** | Most actively developed (26.3-snapshot ports within days); modern builder API plus new config-class/Gson path; itself a Stonecutter workspace (same toolchain as this repo); clear 26.1+ release line | No keybind controller; persistence is manual unless adopting the brand-new v2 config path; largest jar (JIJ'd imageio/quilt-parsers); separate 3.8/3.9 lines complicate per-anchor pins; LGPL-3 |
| **Hand-rolled (vanilla Screen + Gson file)** | Zero external dependencies to track across six anchors; total control over look and the keybind widget; Gson persistence is cheap; no license/bundling concerns | ~250–400 lines plus owning every future vanilla GUI refactor on six anchors (the exact churn the libraries absorb); must fork widget code at the Yarn/Mojang break; screen polish (scrolling, tooltips, undo/reset) is recurring cost |

Consistent pattern across the findings: the no-remap break is survivable for every option, ModMenu wiring is a constant ~6-line cost, and the decisive variables are (1) where the toggle keybind UI comes from, (2) how much screen-building code this repo wants to own across a 15-version span, and (3) tolerance for per-version artifact pinning. Those trade-offs are for ticket #13 to weigh.
